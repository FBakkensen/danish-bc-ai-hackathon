a true story · wednesday 5 august · StefanMaron/BusinessCentral.AL.Runner

Bug report to release:
eleven hours.

AL Runner is the community test runner you will use this afternoon. This is the day it learned to run on Windows.

05:52
Early. Coffee. I want to run my AL tests — and AL Runner is dead on arrival. Not an edge case: it cannot start on Windows, ever, for anyone. The old move here: sigh, write "Linux-only" in the wiki, check back next year.
05:52same minute
Instead, my agent turns the crash into a proper bug report while the coffee brews — stack trace, root cause, minimal repro. I file it as issue #1650 and get on with my day.
10:34
Before lunch, the maintainer answers. Not with a comment. Not with "thanks, we'll look into it." With a pull request: real Windows support.
16:58
v2.0.0.0 ships. The tool that was Linux-only at breakfast is cross-platform by dinner. I ran my tests on it that evening.
+ 8weeks
And here is the uncomfortable part: that was not the exceptional day. We kept that pace for eight weeks — 56 reports from me, 55 fixed, most before the next morning, the fastest in 39 minutes. It stopped feeling like magic. It became the routine.
how?
Neither of us works alone. His repo runs a crew of agents — one triages, two implement test-first, one reviews and merges — and by design, no agent may merge its own work. My reports are drafted by an agent from the raw stack trace. The second-busiest committer on that repo is a bot.

“Green means the runner agrees with itself.”

from that repo's agent rulebook — the bar is higher than what most of us call "tested", not lower

crash telemetry→auto-filed issue→triage agent→2 × impl agents · TDD→orchestrator merges→changelog writes itself

A production crash becomes a merged, tested fix with no human in the required path — and a human can take over any item, at any stage, just by assigning themselves.

  • A scheduled telemetry triage bot queries Application Insights, groups crashes by root cause, uses an LLM to dedupe against open issues, and files structured reports. The bot has its own 354-line test suite.
  • A triage agent makes one pass over new issues and labels them ready or needs-input. It is not allowed to write code, and abstaining ("left for human") is a valid outcome.
  • Two implementation agents work in parallel, each in an isolated git worktree, strict red-first TDD, one open PR at a time. They cannot merge.
  • An orchestrator sanity-reviews each PR against its linked issue and merges. It has merge rights but no edit rights — separation of powers is enforced by tool permissions, not by trust.
  • The assignee field is the human/agent boundary: agents never touch anything assigned to a person, so a human takes over by assigning themselves.
  • The agents' instruction files are versioned, reviewed and improved after every surprise — including one rule written after five documented agent stalls, quoting the exact sentence each agent talked itself into.

Every number on this screen is public: github.com/StefanMaron/BusinessCentral.AL.Runner.

a second story · my own backlog · a normal work item

And that was the exceptional day.

spec
A feature from my backlog, a few weeks ago. Before any code exists, the agent and I argue about proof: what exactly must be true for this to be done? The agreed criteria go back into the work item — in Business Central vocabulary, not AI vocabulary.
red
The tests are written first, and I watch every one of them fail — for the right reason. Only then the implementation, until they pass.
breakit
Then the step that would have sounded absurd two years ago: I ask the agent to sabotage the finished code — eight deliberate defects, one at a time — to prove the tests are guards, not decoration. The tests caught all eight. Behind them, 1,616 unit and 1,060 integration tests stayed green.
scale
None of this was staged for today. Since January I have run more than two thousand of these agent sessions — seven out of ten on Business Central work, about 180 a week this month. It is simply how the work happens now.

“Make sure the new tests test the intent of the prod code — not just to kill the mutant.”

for the record — what each step means
  • Old-school engineering — requirements, design, code review, testing discipline. Still the foundation; agents amplify it, they don't replace it.
  • Prompt engineering — phrasing a request so the agent understands the task.
  • Context engineering — making sure the agent sees the right facts: the work item, the relevant files, the standards that apply.
  • Harness engineering — giving the agent tools it can run and gates it must pass: compiler, analyzers, test runner.
  • Loop engineering — letting the agent iterate against the harness until the evidence is green — or a stop rule fires.
  • Graph engineering — multiple agents with roles, boundaries and handoffs, evidence flowing between them. The AL Runner pipeline you saw earlier.

concept 3 of 3 · the skill contract

Every skill answers
four questions.

Today you will package your engineering knowledge into skills — small, reusable instructions an agent can execute. Every one of them must define:

# the contract — no skill is done without all four Context: where may the agent look? Done: what exact result is required? Verify: how are success and failure proven? Stop: when must it halt and escalate?

If a skill can't answer all four, it isn't a skill yet — it's a hope. And note the red part: today, every skill must be proven with a deliberate failure, not just a success.

how we work today

Five rules for the day.

  • Manual before autonomous.Understand every step by invoking it yourself before any loop runs it for you.
  • Small task, strong harness.The ambition today is the quality of the verification — not the size of the feature.
  • Evidence, or it didn't happen."It should work" is not a result. Which tool ran? Where is the output?
  • Struggle is part of the design.This is not a race and not a prompt contest. Getting stuck productively is the exercise.
  • No false green — ever.Never weaken a test, a rule or a criterion to make a result look good.

And one comfort: the autonomous loop is a stretch goal. A working manual verification ladder already counts as full success.

Work Item 1:
build the harness.

Your first move: read the work item yourself — then make Copilot fetch the same work item through the Azure DevOps MCP server and compare. That's the first climb: human-provided context → tool-enabled context.

From a blank repository, your team builds an AL app, a test app, and four manually invokable skills — each with the four-question contract, each proven with a success and a deliberate failure:

1 compile 2 analyzer 3 test · AL Runner 4 verify-all · fail-fast gates

Five checkpoints, A to E, mark the path — the last one is a combined verification that stops at the first failed gate and passes only when every gate passes.

for the record — checkpoints A–E
  • A — Copilot retrieves work item 13226 through Azure DevOps MCP, and the retrieved content matches what you read manually.
  • B — a repository created from blank contains an app and a separate test app, and both compile.
  • C — the compile and analyzer skills each prove a pass and a deliberate failure, preserving the diagnostics.
  • D — the test skill distinguishes all tests passing, an assertion failure, and a compilation failure — via BusinessCentral.AL.Runner.
  • E — the combined verification skill stops at each deliberately failed gate, shows which gate failed with its evidence, and completes when all gates pass.

Also required: at least one skill improved after behaving unexpectedly — preserve the evidence, diagnose from it, make the smallest fix, retest both paths. Skills must never silently weaken their own rules.

These learning skills are exactly that — learning artifacts. Production work will use a shared, centrally maintained skill set; today is about understanding what such a skill set is made of, so you can use it, supervise it, challenge it and improve it.

Feature: Customer credit evaluation Scenario: Approve an order within the available credit Given an unblocked customer with a credit limit of 10,000 And the customer has an outstanding balance of 4,000 When an order amount of 5,000 is evaluated Then the order is approved Scenario: Approve an order exactly at the available credit Given an unblocked customer with a credit limit of 10,000 And the customer has an outstanding balance of 4,000 When an order amount of 6,000 is evaluated Then the order is approved Scenario: Reject an order exceeding the available credit Given an unblocked customer with a credit limit of 10,000 And the customer has an outstanding balance of 4,000 When an order amount of 6,001 is evaluated Then the order is rejected And the rejection reason explains that the available credit is insufficient Scenario: Reject an order when the balance already exceeds the credit limit Given an unblocked customer with a credit limit of 10,000 And the customer has an outstanding balance of 11,000 When an order amount of 1 is evaluated Then the order is rejected And the rejection reason explains that the available credit is insufficient Scenario: Reject an order for a blocked customer Given a customer that is blocked for sales transactions And the customer has sufficient available credit When an order amount of 1,000 is evaluated Then the order is rejected And the rejection reason explains that the customer is blocked Scenario: Reject an order amount of zero Given an unblocked customer with sufficient available credit When an order amount of 0 is evaluated Then the evaluation fails with a clear validation error Scenario: Reject a negative order amount Given an unblocked customer with sufficient available credit When an order amount of -1 is evaluated Then the evaluation fails with a clear validation error

Every scenario runs the full TDD cycle: observe the test failing for the expected reason → smallest implementation → green → refactor → complete verification workflow. Rejections must carry a useful reason; zero and negative amounts are validation errors, not business rejections.

The optional autonomous loop must: create or update tests before implementation, run combined verification after changes, preserve tests and analyzer configuration, stop on unsupported functionality or after the agreed attempt cap, and report changes, verification, assumptions and risks. It never commits or changes acceptance criteria without approval.
