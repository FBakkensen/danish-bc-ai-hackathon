METR measures the length of tasks AI agents can complete autonomously; the measured doubling time is roughly seven months (metr.org). The rows in the second table are observed working practices, not a ranking — teams at different rows use the same words (agents, cost, quality) and report different realities, which is why conversations about "whether the AI spend is worth it" so often talk past each other.

The economics are asymmetric: the cost of agentic development is itemized and lands on an invoice now; the gain arrives later, and only after the way of working changes. That asymmetry is a property of the transition, not a verdict on it.

■ today's steps: context · harness · loop · The six steps: Freddy Kristiansen, The Engineering Stairway to Heaven

for the record — the steps, and the three operating levels
  • Old-school engineering — requirements, design, review, testing discipline. The foundation; agents amplify it, they don't replace it.
  • Prompt engineering — phrasing a request so the agent understands the task.
  • Context engineering — the agent sees the right facts: the work item, the relevant files, the standards that apply.
  • Harness engineering — tools the agent can run and gates it must pass: compiler, analyzers, test runner.
  • Loop engineering — the agent iterates against the harness until the evidence is green, or a stop rule fires.
  • Graph engineering — multiple agents with roles, boundaries and handoffs. The system from the climate section.

The same climb, seen as operating levels: Level 1 — ask (paste context in, judge output by eye), Level 2 — equip & loop (tools, gates, a contract; the agent iterates against evidence), Level 3 — orchestrate (several agents, enforced boundaries, human supervision). Most BC work today happens at Level 1. Today's target is Level 2. Production work will use a shared, centrally maintained skill set — today is about understanding what such a set is made of, so you can use it, supervise it, challenge it and improve it.

Every skill answers
four questions.

# the contract — required for every skill built today Context: where may the agent look? Done: what exact result is required? Verify: how are success and failure proven? Stop: when must it halt and escalate?
for the record — why the contract matters

A skill is a small, reusable instruction an agent can execute — compile this, analyze this, run these tests. The contract is what separates a skill from a hope: without Verify, green means nothing; without Stop, the agent improvises at exactly the moment it shouldn't.

A flawed skill is worse than a flawed line of code: a code defect hits one place, a flawed skill silently affects every future invocation. That is why every skill you build today is proven with a success and a deliberate failure — and why a skill must never weaken its own rules.

Five rules for the day.

  • Manual before autonomous.Invoke every step yourself before any loop does.
  • Small task, strong harness.Ambition goes into verification, not feature size.
  • Evidence, or it didn't happen.Which tool ran? Where is the output?
  • Struggle is part of the design.Not a race. Not a prompt contest.
  • No false green — ever.Never weaken a test to look good.

The autonomous loop is a stretch goal — a proven manual ladder is full success.

for the record — the feature, in Gherkin
Feature: Customer credit evaluation Scenario: Approve an order within the available credit Given an unblocked customer with a credit limit of 10,000 And the customer has an outstanding balance of 4,000 When an order amount of 5,000 is evaluated Then the order is approved Scenario: Approve an order exactly at the available credit Given an unblocked customer with a credit limit of 10,000 And the customer has an outstanding balance of 4,000 When an order amount of 6,000 is evaluated Then the order is approved Scenario: Reject an order exceeding the available credit Given an unblocked customer with a credit limit of 10,000 And the customer has an outstanding balance of 4,000 When an order amount of 6,001 is evaluated Then the order is rejected And the rejection reason explains that the available credit is insufficient Scenario: Reject an order when the balance already exceeds the credit limit Given an unblocked customer with a credit limit of 10,000 And the customer has an outstanding balance of 11,000 When an order amount of 1 is evaluated Then the order is rejected And the rejection reason explains that the available credit is insufficient Scenario: Reject an order for a blocked customer Given a customer that is blocked for sales transactions And the customer has sufficient available credit When an order amount of 1,000 is evaluated Then the order is rejected And the rejection reason explains that the customer is blocked Scenario: Reject an order amount of zero Given an unblocked customer with sufficient available credit When an order amount of 0 is evaluated Then the evaluation fails with a clear validation error Scenario: Reject a negative order amount Given an unblocked customer with sufficient available credit When an order amount of -1 is evaluated Then the evaluation fails with a clear validation error

Every scenario runs the full TDD cycle: observe the test failing for the expected reason → smallest implementation → green → refactor → complete verification workflow. Rejections carry a useful reason; zero and negative amounts are validation errors, not business rejections.

Deliberate-defect proof: break the finished implementation once — the recommended defect is flipping the exact-boundary behaviour — and confirm a test catches it. The optional autonomous loop must work test-first, verify after changes, preserve tests and analyzer configuration, stop on unsupported functionality or after the agreed attempt cap, and report changes, verification, assumptions and risks.
